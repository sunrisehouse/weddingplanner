# weddingplanner

웨딩홀 투어를 기록하고 나란히 비교하는 웹앱.

투어 현장에서 서서 한 손으로 적는 것을 기준으로 만들었습니다.
업체와 금액을 앱이 제안하지 않고, 직접 적은 것만 저장하고 계산합니다.

## 첫 방문 — 한 화면에 질문 하나

처음 열면 질문 4개를 **한 화면에 하나씩** 물어봅니다. 전부 선택지로 고릅니다.

**묻는 건 자료의 큰 항목뿐입니다.** 체크리스트 인쇄면의 `구분` 열이 그대로 질문이 됩니다 —
웨딩홀 · 스드메 · 허니문 · 혼수. 청첩장 · DVD · 주례 · 폐백음식처럼
자료에서 **'기타'로 묶인 작은 항목은 묻지 않습니다.**

| | 질문 | 선택지 |
|---|---|---|
| 1 | **웨딩홀은 정하셨나요** | 계약 / 투어 중 / 아직 |
| 2 | 스드메는 어디까지 하셨나요 | 계약 / 상담 중 / 아직 |
| 3 | 허니문은 정하셨나요 | 예약 / 알아보는 중 / 아직 |
| 4 | 혼수는 어디까지 하셨나요 | 거의 정함 / 알아보는 중 / 아직 |

### 예식일을 먼저 묻지 않습니다 — 웨딩홀에서 나오니까

예식일은 **웨딩홀을 계약해야 정해집니다.** 그래서 웨딩홀이 첫 질문이고,
그 답에 따라 시점을 다른 정밀도로 받습니다.

| 웨딩홀 답 | 다음 화면 | 저장 |
|---|---|---|
| 계약했어요 | 예식일이 언제인가요 — 날짜 입력 | `ceremonyDate` |
| 투어 중 · 아직 | 예식은 언제쯤 생각하세요 — **년 · 월 선택** | `ceremonyMonth` |

두 화면 모두 진행 번호(`1/4`)를 차지하지 않습니다. 웨딩홀 질문의 후속이니까요.
`아직 모르겠어요`로 건너뛸 수 있고, 그러면 시점을 아예 따지지 않습니다.

**달만 알면 달로만 답합니다.** 없는 날짜를 만들어 쓰지 않습니다.

| | 홈에 뜨는 것 | 마감 |
|---|---|---|
| 날짜를 알 때 | `D-156 · 1월 20일 (수)` | `3월 26일까지 예약하세요` |
| 달만 알 때 | `2027년 5월 · 예정 · 약 9개월 남음` | `2026년 7월까지 예약하세요` |

달 기준일 때는 **`웨딩홀 예약하시면 날짜로 바꿔드릴게요`** 를 같이 적습니다.
나중에 계약하고 날짜를 넣으면 달 추정치는 지워지고 날짜 기준으로 바뀝니다.
`시기 수정`(D-day 카드)으로 언제든 고칠 수 있습니다.

### 답으로 하는 일 — 언제까지 해야 하는지 알려주기

예식 시점과 준비 상태를 예약 시점에 대보고, **시점이 지난 것만 짚어줍니다.**

| 항목 | 앱이 안내하는 시점 |
|------|--------------------|
| 웨딩홀 | 늦어도 10개월 전에 예약 |
| 스드메 | 10~12개월 전에 예약 |
| 허니문 | 6~8개월 전에 예약 |
| 혼수 | 예단은 3개월 전에 준비 |

혼수의 한복은 **촬영 2개월 전**, 가전·가구는 **입주 2~3개월 전** 기준이라
예식일로 계산하지 않고 그 사실만 알려줍니다.

무엇을 먼저 하라고 순서를 정해주지는 않습니다. **시점이 지난 것만** 짚습니다.

#### 말투 — 서비스가 안내한다, 전해 듣고 알려주지 않는다

숫자의 출처는 **박람회 자료 `비고` 열**이고, 근거는 [docs/01-checklist.md](docs/01-checklist.md)와
`app/js/store.js`의 `PREP` 주석에 남겨둡니다. 새 숫자를 추측해서 넣지 않기 위한 기록입니다.

**하지만 화면에서는 출처를 말하지 않습니다.**

| | |
|---|---|
| ✕ | "자료 기준 최소 10개월 전 예약" |
| ✓ | "늦어도 10개월 전에 예약하세요" |
| ✕ | "투어에서 물어볼 것 보기" |
| ✓ | "웨딩홀 투어 준비하기" |

앱을 쓰는 사람에게 필요한 건 **지금 뭘 하면 되는지**입니다.
어디서 본 내용인지는 우리가 관리할 문제입니다.

다음에 할 일도 앱이 정해서 버튼 하나로 줍니다 — 목록을 던져놓고 알아서 보라고 하지 않습니다.

| 웨딩홀 상태 | 다음 버튼 |
|---|---|
| 아직 안 알아봤어요 | 웨딩홀 투어 준비하기 |
| 투어 다니는 중이에요 | 투어 기록 시작하기 |
| 계약했어요 | 계약한 웨딩홀 기록하기 |

- 예식 시기를 모르면 시점을 따질 수 없으니 **계산하지 않고 그렇다고 말합니다**
- 모든 질문에 **`건너뛰고 바로 시작하기`** 가 있습니다.
  건너뛴 항목은 `안 정하셨어요`로 남아 **"아직 안 알아봤다"와 구분됩니다**
- 뒤로 가기로 답을 고쳐도 되고, 끝난 뒤에도 바꿀 수 있습니다

## 홈은 전체, 항목은 탭에서

최상위 화면은 **탭 네 개**입니다. 홈에는 전체로 봐야 하는 것만 두고,
항목별 관리는 각자의 탭에서 합니다.

```
[ 🏠 홈 ]   [ 💐 웨딩홀 ]   [ 📸 스드메 ]   [ ✈️ 허니문 ]     ← 하단 탭
   #/          #/venues       #/sdm          #/honeymoon
                 ├ #/new        ├ #/sdm/new
                 ├ #/v/:id      └ #/sdm/v/:id
                 └ #/guide
   #/when   예식 시점만 고치는 화면
   #/honsu  혼수 (탭 없이 홈에서 들어감)
```

혼수는 탭에 넣지 않았습니다. 예약이 아니라 **품목별로 할지 말지를 정하는 일**이라
계속 오갈 화면이 아니고, 탭 다섯 개는 폰에서 좁습니다.
홈의 준비 현황에서 눌러 들어갑니다.

### 준비 현황에서 눌러서 들어갑니다

홈의 네 줄이 **각 항목의 관리 화면으로 가는 버튼**입니다.

| 줄 | 가는 곳 |
|---|---|
| 웨딩홀 | `#/venues` — 투어 기록 · 비교표 · 예약 확정 |
| 스드메 | `#/sdm` — 업체 비교 · 계약 확정 · 촬영일 |
| 허니문 | `#/honeymoon` — 여행 일정 · 비용 |
| 혼수 | `#/honsu` — 품목별 준비 / 생략 |

**진행 상태는 각 항목 화면에서 고칩니다.** 상태 하나 바꾸려고
온보딩 네 질문을 다시 걷게 하지 않습니다 (그래서 `답 수정` 링크를 없앴습니다).

### 항목마다 단계가 있다 — 비교 → 예약 확정

웨딩홀과 스드메는 **여러 곳을 비교한 뒤 한 곳으로 정하는** 일입니다.
그래서 화면이 단계마다 달라집니다.

| 단계 | 화면 | 다음 |
|---|---|---|
| **1 알아보기** | 확인할 것을 먼저 알려줌 | `기록 시작하기` |
| **2 비교** | 후보 목록 + 비교표 | 후보마다 `이걸로 예약했어요` |
| **3 확정** | 정한 곳 · 계약 후에 필요한 것 | `다시 비교하기`로 되돌릴 수 있음 |

**확정하면 진행 상태가 같이 넘어갑니다.** 두 곳에 따로 적게 하지 않습니다.
`다시 비교하기`를 누르면 상태가 `진행 중`으로 돌아가고, **적어둔 기록은 그대로** 남습니다.

웨딩홀을 확정하면 **예식일을 바로 물어봅니다** — 예식일이 계약에서 나오니까요.

비교표에는 확정한 곳도 함께 남겨둡니다. 무엇과 비교해서 정했는지가 기록이니까요.

### 스드메 — 실제 예상은 패키지 금액이 아니다

자료의 요지는 **"계약 총액만 보면 실제 지출을 알 수 없다"** 입니다.
그래서 후보마다 계약서의 **별도 항목 9개 금액**을 따로 받고, 이렇게 계산합니다.

```
실제 예상 = 패키지 금액 + 적어둔 별도 비용
```

비교표에 별도 항목을 **한 줄씩 나란히** 놓습니다. 패키지가 싼 곳이
별도를 더 받으면 그게 표에서 보입니다. 적어둔 것만 더하고,
**안 적은 항목은 개수로 알립니다** (`별도 5개 미입력`).

별도 항목: 원본 데이터 · 선수정본 · 헬퍼비(촬영/본식) · 드레스 투어비 ·
출장비(촬영/본식) · 얼리스타트 · 테이블 비용.

#### 계약 후에는 촬영일이 기준이 된다

자료에서 중요한 또 하나는 **촬영일이 예식일과 별개의 기준일**이라는 사실입니다.
위약금과 중도금이 여기 걸립니다. 확정 단계에서 촬영일을 넣으면 세 날짜가 나옵니다.

| | 계산 | 근거 |
|---|---|---|
| 위약금 시작 | 촬영 90일 전 | 계약서 인쇄면 |
| 중도금 70% | 촬영 60일 전 | 〃 |
| 잔금 20% | 본식 60일 전 | 〃 |

준비 단계는 일정표 인쇄면에서 그대로 왔습니다 — 드레스샵 투어(2~3곳 · 샵당 1시간 ·
4벌 피팅 후 1벌 홀딩) · 촬영 가봉(6벌 피팅 후 3벌) · 본식 가봉(4벌 피팅 후 1벌 · 부케 결정).

### 허니문 · 혼수 — 자료에 있는 만큼만

허니문은 자료에 **한 줄**뿐입니다(신혼여행비 · 여행지 추가지출 · 예비비(선물비용) / 6~8개월 전).
그래서 여행지 · 출발 · 귀국 날짜와 그 세 가지 금액만 받습니다.
여권·비자 같은 항목은 자료에 없으므로 만들어 넣지 않았습니다.
출발일을 넣으면 `예식 2일 후 출발`, 귀국일까지 넣으면 `7박 8일`을 계산합니다.

혼수는 품목마다 **준비 / 생략 / 미정**을 남깁니다. 예단·한복처럼
안 하기로 정하는 경우가 있어서 `생략`이 따로 필요합니다.
한복은 촬영 2개월 전, 가전·가구는 입주 2~3개월 전 기준이라 예식일로 세지 않습니다.

### 웨딩홀 탭 · 기록이 0곳일 때

기록이 0곳이면 빈 비교표 대신 갈래를 나눕니다.

| | 다음 화면 |
|---|---|
| **투어 다녀왔어요** | 기록 폼 |
| **아직 안 가봤어요** | 웨딩홀 투어 준비 |
| 예시로 먼저 둘러보기 | 비교표가 어떻게 보이는지 (한 번에 지울 수 있음) |

비교표는 2곳 이상이어야 의미가 생기는데 첫 방문자는 0곳입니다.
그래서 **예시 데이터**를 넣어볼 수 있게 하고, `예시` 표시를 달아 언제든 지웁니다.

**앱 소개는 화면에 두지 않습니다.** "이 앱이 하는 일 / 안 하는 일" 목록을
깔아두면 읽을 거리만 늘고, 정작 할 일이 뒤로 밀립니다.

기록이 이 브라우저에만 저장된다는 것은 계속 말합니다 — 나중에 알면 이미 늦습니다.

## 하는 일

- 웨딩홀별로 **홀 이름 · 투어 날짜 · 홀 사용료 · 꽃장식 · 식대 · 보증인원** 기록
- 포함 여부를 **있음 / 없음 / 모름** 3단으로 선택
  (`모름`이 따로 있어야 "안 물어본 것"과 "없는 것"이 구분됩니다)
- 예상 합계 자동 계산 — `홀 사용료 + 꽃장식 + (보증인원 × 식대)`
  값이 하나라도 비면 **계산 불가**로 두고 억지로 채우지 않습니다
- 2곳 이상 기록하면 비교표가 나타납니다
- 견적서 사진 첨부
- 입력 즉시 자동 저장
- **웨딩홀 투어 준비** — 투어에서 확인할 것을 짚어주고, 확인한 그대로 비교표가 됩니다
- **예약 시점이 지난 큰 항목** 알림 (웨딩홀 · 스드메 · 허니문 · 혼수)
- **스드메** — 업체별 견적 비교(패키지 + 별도 9개 = 실제 예상), 계약 확정,
  촬영일에서 위약금 경계 · 중도금 · 잔금 날짜 계산
- **허니문** — 여행 일정(예식과의 간격 · 몇 박 며칠)과 비용 합산
- **혼수** — 품목별 준비 / 생략 / 미정

**앱은 순위를 매기거나 추천하지 않습니다.** 적어둔 것을 나란히 놓아줄 뿐입니다.

## 안 하는 일

| | 이유 |
|---|---|
| 시세 · 평균가 제시 | 업체 · 지역 · 시기마다 달라서, 어떤 기준값을 보여줘도 틀린 숫자를 믿게 만듭니다 |
| 업체 추천 · 평점 | 판단은 쓰는 사람이 합니다 |
| 금액 기본값 채우기 | 채워두면 결국 앱이 가격을 제안하는 셈이 됩니다 |

## 저장

**localStorage에 저장합니다.** 서버도 로그인도 없이 바로 쓸 수 있는 대신 한계가 있습니다.

| 한계 | 실제로 생기는 일 |
|------|------------------|
| 브라우저 하나에만 저장 | 다른 기기에서 못 봅니다 |
| 기기를 바꾸면 사라짐 | 폰을 바꾸면 안 따라옵니다 |
| 브라우저 데이터 삭제 시 소실 | "인터넷 사용 기록 삭제"로 날아갑니다 |
| 용량 5MB 안팎 | 사진 몇 장이면 찹니다 |

그래서 이렇게 대응했습니다.

- **JSON 내보내기 / 불러오기** — 유일한 백업이자 기기 이동 수단이라 처음부터 넣었습니다
- **사진은 IndexedDB에 분리** — localStorage는 문자열만 담기고 한도가 작아,
  사진이 텍스트 기록까지 밀어내는 것을 막았습니다
- **저장 실패 시 알림** — 용량이 차면 조용히 넘어가지 않고 알립니다
- **`store.js` 뒤로 숨김** — 앱 코드는 localStorage를 직접 건드리지 않습니다.
  서버로 옮길 때 이 파일만 교체하면 됩니다

### 여럿이 함께 보려면

localStorage로는 안 됩니다. 필요해지면 **Supabase** 무료 티어가 이 구조에 잘 맞습니다 —
정적 사이트에서 바로 붙고, anon 키는 공개돼도 되며 RLS로 접근을 막습니다.
`store.js` 하나만 바꾸면 됩니다.

## 배포

`.github/workflows/pages.yml` 이 `main` 푸시마다 `app/` 을 GitHub Pages로 올립니다.

처음 한 번만 설정이 필요합니다.

1. `Settings → Pages → Source` 를 **`GitHub Actions`** 로 변경
2. 무료 플랜에서는 저장소가 **public** 이어야 합니다

private으로 두면서 배포하려면 **Cloudflare Pages** 나 **Netlify** 를 쓰면 됩니다
(둘 다 private 저장소를 무료로 배포합니다).

> ⚠️ **개인적인 기록은 이 저장소에 두지 마세요.**
> 계약 금액, 업체명, 준비하면서 내린 결정 같은 것은 앱 안에서만 다루면 됩니다.
> 앱의 데이터는 브라우저에만 저장되고 저장소로 올라가지 않습니다.
